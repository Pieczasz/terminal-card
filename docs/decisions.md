# Decisions

One record per non-obvious choice. Each says what the situation was, what was
decided, what that costs, and where the code is. The date and commit are the ones
`git log -S'<symbol>' --reverse` names as introducing the change; where a decision
was refined later, both are given.

These are **not** a plan. They are the reasons behind code that already exists, so
the next person can tell a deliberate constraint from an accident. If you change
one of these, change the record too - a stale reason is worse than none.

Contracts and invariants live in [`architecture.md`](architecture.md). This file
is only the *why*.

## 1. One mutex per engine

*2026-08-28, `d4b9497` "merge engine locks, closed flag, turnSeq-checked auto-play".*

**Context.** The engine has a turn cursor, a timer, a deadline, a missed-turn map
and a `*State`. They are always read together - deciding whose turn it is means
reading the cursor and the seat list in the same breath. Separate locks would mean
an ordering to get right on every path.

**Decision.** `Engine.mu` is the only lock. It covers the clock fields **and**
`State`. `State` has no lock of its own, and every `Rules` method,
`WithState` callback and `Frame` callback runs with it held.

**Consequences.** Coarse: a `Frame` from one session briefly blocks a `Submit`
from another. That is acceptable because everything under the lock is in-memory
map and slice work; nothing does I/O. In exchange there is exactly one lock order
to remember (manager → lobby → engine) and no fourth level.

**Where.** `internal/game/engine.go` - the comment on the `Engine` struct says it.
`internal/game/state.go` says the same from the other side.

## 2. Rules never call back into the engine

*Same commit as #1.*

**Context.** Every `Rules` method runs with `Engine.mu` held. A rules
implementation that called `engine.SubmitAction` or `engine.Snapshot` would
deadlock on the mutex it is already under.

**Decision.** Rules must never call the engine. Enforced **structurally** rather
than by review: `Rules` methods receive only `*State`, and `State` carries no
engine handle. There is nothing to call.

**Consequences.** Rules may mutate `*State` freely, which is what makes them
readable. The cost is that a rules set cannot ask the engine a question - anything
it needs has to be on `State` or in `State.Extra`. Adding an engine pointer to
`State` for convenience would silently remove the guarantee, so do not.

**Where.** `internal/game/rules.go`, `internal/game/state.go`. The doc comment on
`Engine.WithState` repeats the warning for the other caller class.

## 3. Latest-wins broadcaster, and `Subscribe` returns an error

*Backpressure policy 2026-07-23, `9726b97`. Error-on-subscribe 2026-08-08, `41ed85d`.*

**Context.** One engine fans events out to every seated player's SSH session. A
slow or wedged client must not stall the table.

**Decision A - latest-wins.** `Broadcast` holds the mutex, tries a non-blocking
send on each subscriber's 256-deep buffer, and on a full buffer **drops the oldest
and enqueues the newest**. Correct here because every event is a *cue to re-read a
snapshot*, not a delta that has to be applied in sequence: losing intermediate
frames costs nothing as long as the most recent one arrives.

**Decision B - error, not a closed channel.** `Subscribe` returns `ErrClosed` or
`ErrAtCapacity` rather than handing back a pre-closed channel. A closed channel is
indistinguishable from a finished game, so a caller given one would stop receiving
with no way to tell which happened.

**Consequences.** Every caller has to handle a subscribe error. Views surface it
in their own error line and tell the player to rejoin; the lobby logs it loudly,
because there it means a match result will not be persisted. Dropped messages are
counted (`Dropped()`) and logged **once** per subscriber, not per message - a
stuck subscriber would otherwise turn every broadcast into a log write under the
lock.

**Where.** `internal/broadcaster/broadcaster.go`. Capacity sizing is at
`game.NewEngine` (`len(players) + 8`) and `lobby.Manager.New`.

## 4. `turnSeq`: a generation counter fences the turn clock

*Clock 2026-08-08, `41ed85d`. Fencing 2026-08-28, `d4b9497`.*

**Context.** A `time.AfterFunc` timer fires on its own goroutine, takes the lock,
computes a safe move, **drops the lock**, and re-takes it to submit. In that gap
the player can act for themselves. Without a fence they are charged a miss for a
turn they took, and the auto-play lands as a second move.

**Decision.** `stopTurnTimerLocked` increments `turnSeq`, and
`armTurnTimerLocked` calls it first - so every cursor change invalidates timers
already in flight. A timer captures the generation when armed;
`submitTimedOutAction` refuses a mismatch with `errStaleTurn`, and
`removeIfStillIdle` re-checks the same generation before taking a seat.

**Consequences.** `turnSeq` is the whole re-check, and that is deliberate: every
path that clears a miss count also settles the cursor, and settling the cursor
bumps the sequence. So a matching sequence proves the count was not cleared. A
*rejected* action clears nothing and bumps nothing, which is exactly why spamming
garbage cannot dodge removal.

**Where.** `internal/game/turnclock.go` - the comment on `removeIfStillIdle`
states the argument in full. Tests:
`internal/game/engine_timeout_test.go`.

## 5. `BoundEngine` is a façade, not a capability

*2026-07-18, `e879142` "close empty lobbies and bind game actions to sessions".*

**Context.** A game view needs to submit actions and read state. Handing it the
`*Engine` means every view can act as any player and read every hand.

**Decision.** `game.Bind(engine, playerID)` returns a session-scoped handle that
submits only as that player and returns only that player's hand. But
`BoundEngine.Engine()` still hands back the whole engine, and poker uses it.

**Consequences.** This is explicitly **not** a security boundary - a view that
wants whole-table state can have it, because rendering a card table means
rendering every seat. What the façade buys is that the *default* path is the safe
one, so reaching past it is a visible detour in review, and the redaction becomes
the view's named, testable job. In poker that function is `buildSeats`, and it has
its own test file.

**Where.** `internal/game/bound.go` (the comment on `Engine()`),
`internal/tui/views/game/poker/model.go` `buildSeats`,
`internal/tui/views/game/poker/redaction_test.go`.

## 6. `catalog.All` is the single registration point, and the lockstep hazard is accepted

*2026-08-01, `395fc06` "register game rules and TUI view in one place".*

**Context.** A game needs a rules factory (for `game.Registry`, built in
`cmd/server/main.go`) and a TUI view constructor (for the route table, built in
`internal/tui/app.go`). Two lists means a game can be half-registered.

**Decision.** One slice, `catalog.All`, whose `Entry` carries both. Both consumers
read the same slice.

**Consequences.** A game cannot be registered without a view: `catalog_test.go`
fails on a missing field or a duplicate slug. But **copying an entry and changing
only the `Rules` field still compiles and still passes** - the types match. That
hazard is accepted rather than engineered away, because the alternative (a
registry keyed by a type parameter, or codegen) costs more than the one line of
attention it saves. The pair is kept in lockstep by hand, and the tests
`TestAll_NamesArePersistedAndFrozen` and `TestAll_SlugsMatchTheMigrationBackfill`
catch the cases that actually corrupt data.

**Where.** `internal/catalog/catalog.go`, `internal/catalog/catalog_test.go`.

## 7. A game's identity in the database is its slug

*2026-09-19, `56c561c`; migration `000005_game_slug`.*

**Context.** `games` was keyed by display `name`, with `CREATE UNIQUE INDEX
idx_games_name`. Renaming a game in the catalog created a *second* `games` row and
orphaned every `rankings` row attached to the first.

**Decision.** `games.slug` is the identity. `getOrCreateGame` upserts
`ON CONFLICT (slug)` and refreshes `name` on every write, so a rename reaches the
leaderboard without moving a rating. Migration `000005` backfills the five
existing slugs explicitly and **drops** `idx_games_name`.

**Consequences.** The slug is permanent. Changing one later is a data migration,
not a rename - `CONTRIBUTING.md` says so where a contributor will read it. The two
halves travel together as `db.GameRef{Slug, Name}` so a caller cannot supply one
without the other, and `Module.Name` stays the in-memory registry key so the lobby
never has to know about slugs.

**Where.** `internal/db/games.go` (`GameRef`), `internal/repository/match.go`
`getOrCreateGame`, `internal/db/migrations/000005_game_slug.up.sql`.

## 8. Account ids are UUIDv7, generated by Postgres 18

*2026-09-20, `f434649` "account ids are UUIDv7 via Postgres 18 uuidv7() and the stdlib uuid package".*

**Context.** `users.id` was a `BIGSERIAL`. A sequential account id is enumerable:
it leaks how many accounts exist, in what order they registered, and it makes an
id guessable from a neighbour's. The id also appears in logs as `player_id`.

**Decision.** `users.id UUID PRIMARY KEY DEFAULT uuidv7()` - version 7, not 4, and
not `gen_random_uuid()`.

**Why not `BIGSERIAL`.** Enumeration, as above.

**Why v7 and not v4.** A v7 UUID is time-ordered in its high bits, so inserts land
at the right-hand edge of the primary-key B-tree instead of scattering across it.
A random v4 primary key fragments the index and dirties a new page per insert. v7
keeps the locality of a sequence while keeping the unguessability of a random id.

**Why Postgres generates it.** `uuidv7()` is a Postgres 18 built-in, so the
database can fill the column for any writer, including a raw `INSERT`. Go supplies
one too - `User.BeforeCreate` sets `uuid.NewV7()` when the field is zero - so
neither side depends on the other being present.

**Consequences.** Postgres **18** is now a hard floor, and the rewritten `000001`
will checksum-fail against a volume created under an older major: an upgrade means
recreating the volume or `pg_upgrade`. The Go side uses the **stdlib** `uuid`
package (`import "uuid"`, Go 1.27) - there is no `github.com/google/uuid` in the
direct requirements. Because stdlib `uuid.UUID` has no `database/sql` Scanner or
Valuer, GORM needs a serializer, registered once as `stduuid`, and raw query
parameters go through `uuid.String()` - pgx will not encode the `[16]byte`
as a `uuid` on its own.

**Where.** `internal/db/users.go` (the `User.ID` tag and `BeforeCreate`),
`internal/db/uuid_sql.go` (the serializer and why it exists),
`internal/db/migrations/000001_init.up.sql` line 2,
`internal/repository/match.go` `uuidStrings`.

## 9. The provisional rule is per pair, not per account or per table

*Provisional accounts 2026-08-28, `eee8020`. Made per-pair 2026-09-19, `de1131e`.*

**Context.** Identity here is a free SSH keypair, so a fresh 1500-rated opponent
costs nothing to mint. Beating one must not pay. The first implementation froze
the *whole table* when any seat was provisional.

**Decision.** `elo.Player.Provisional` is set by the repository from
`MatchesPlayed < provisionalMatches` (5; a missing ranking row counts as
provisional). `elo.Calculate` scores adjacent pairs, and
`unpaidAgainstProvisional` clamps the **established** side's delta to at most zero
on a mixed pair - gains zeroed, losses untouched. The provisional side always
moves.

**Consequences.** This deliberately breaks Elo's zero-sum property for that pair.
That is the point: an unfarmable ladder is worth more than the conservation
property. Both halves are needed. Without the "losses still count" half, an
established player could seat an alt to freeze their own rating, and the anti-farm
rule would become a shield. Because the provisional side always moves, a new
account converges on its real rating over its first five matches - and
`matches_played` increments even when no rating is written, which is what lets it
graduate.

**Where.** `internal/elo/elo.go` `unpaidAgainstProvisional` and the comment on
`Player.Provisional`; `internal/repository/match.go` `provisionalMatches = 5` and
`calculateNewElos`.

## 10. The anti-farm cap counts pairs, across every game

*2026-08-28, `eee8020`. Made per-pair rather than per participant set 2026-09-19, `56c561c`.*

**Context.** Two accounts trading ranked wins is either farming or a private
rivalry; either way the ladder should stop paying. The first version counted
repeats of the **exact participant set**, so `{A,B}`, `{A,B,C}` and `{A,B,D}` each
had their own budget and two accounts could farm forever by rotating a third alt
through the table.

**Decision.** `repeatedPairCountLast24h` counts, over ranked non-deleted matches
in the last 24 hours, the highest co-occurrence of any **pair** of players at this
table, **across every game**. At `maxSamePairingPerDay` (3) the table is *damped*.

**Consequences.** The count is per pair but the effect is table-wide: one
over-budget pair damps every seat, because there is a single `damped` flag.
A damped table still writes `matches_played` and records the match; it just writes
no `elo` and no delta. Switching game does not reset the budget, which is why the
window spans all five. Because the count is read inside the transaction,
`lockPairing` has to be held first, or two concurrent finalizes sharing a seat both
read an undamped count.

**Where.** `internal/repository/match.go` - `maxSamePairingPerDay`,
`repeatedPairCountLast24h`, `worstPairCount`, and the damping branch inside
`updateRankingsTx`.

## 11. Three end states are recorded without Elo

*`EndReasonAbandoned` 2026-08-28, `d4b9497`.*

**Context.** `EventGameEnded` carries an `EndReason`, and not every ending is a
result.

**Decision.** `rated := req.isRanked && !m.isShuttingDown() && reason !=
EndReasonRulesError && reason != EndReasonAbandoned`. The match is still written -
as casual history - in all three cases.

- **Shutdown.** SSH teardown order, not play, decided who was left holding cards.
- **`EndReasonRulesError`.** The state may be half-applied; it must not move the
  ladder.
- **`EndReasonAbandoned`** (every seat left). Standings are then just reverse leave
  order, so rating them pays the last person to quit.

`EndReasonForfeit` - last player standing, everyone else left - **is** rated. It
is an honest result.

**Consequences.** A player cannot tell a damped match from an unrated one from the
outside; both read as "no Elo change". `unratedReason` logs which of the three it
was, and the metric label distinguishes them. An abandoned match with no standings
at all writes nothing and counts as `dropped`.

**Where.** `internal/lobby/finalize.go` - the gate, `unratedReason`,
`endReasonLabel`. `internal/game/action.go` for the enum.

## 12. Players who left rank strictly below players who stayed

*2026-09-19, `b68ed91` "rank players who left strictly below seated players".*

**Context.** `StandingScorer` lets equal results share a finishing place, so a
genuine draw does not take rating off one of the two. But a player who left was
scored against a state they are no longer in.

**Decision.** `standingsLocked` appends `LeftPlayers` **after** the seats the rules
placed, in reverse leave order. `placesLocked` guards the tie branch with
`left[p.ID] == left[standings[i-1].ID]`, so a leaver can never share a place with
a seated player.

**Consequences.** A rage-quit cannot become a rated draw. Two leavers with the
*same* score do still share a place, because splitting them would mint Elo between
two people who both quit.

**Where.** `internal/game/engine.go` `standingsLocked` and `placesLocked`.

## 13. The finalize snapshot is taken when the game starts

*2026-09-06, `b2528ed` "extract finalize/disconnect".*

**Context.** A lobby reopens after a hand ends, and the leader can immediately
change the game, flip ranked off, and start again. The finalize for the *previous*
hand may still be in flight.

**Decision.** `watchGameLocked` builds `finalizeRequest{lobbyCode, game, isRanked,
startedAt}` at **subscribe** time, before the first card is dealt, and
`startGameLocked` sets `l.startedAt` immediately before that. The watcher carries
the snapshot to `Manager.finalizeFinishedGame`.

**Consequences.** A reconfiguration after the hand ends cannot rewrite the
finished match's game, ranked flag or duration. The cost is one small struct
copied per match, and the discipline that nothing in the finalize path may read
live lobby settings.

**Where.** `internal/lobby/lobby.go` `startGameLocked` / `watchGameLocked`,
`internal/lobby/finalize.go`.

## 14. A mid-game seat survives 90 seconds, with the engine auto-playing

*2026-08-28, `1c8f407` "90s disconnect grace holds a mid-game seat; reconnect resumes the match".*

**Context.** A wifi blip mid-hand used to forfeit the match. Leaving the seat
indefinitely instead would let one person freeze a table.

**Decision.** A dropped session calls `Manager.DisconnectPlayer`, not
`LeaveLobby`. Mid-game it arms `DisconnectGrace` (90 seconds). The engine keeps
auto-playing the absent seat through `TimeoutAction`, and `MaxMissedTurns` (3) is
the backstop that takes the seat even inside the grace window.
`Manager.ResumePlayer` - wired into the TUI's initial route - cancels a pending
leave and lands the player back at the table.

**Consequences.** The other players are never made to wait: three 30-second
auto-played turns is the worst case, and the clock keeps running. A waiting-lobby
seat and any seat during shutdown still leave immediately, because there is no
hand to come back to. The hold is released at three points, not one - its timer,
`releaseHeldSeats` when the hand ends, and `BeginShutdown` - because a still-armed
hold keeps the player out of every other table and this one unable to reach
all-ready.

**Where.** `internal/lobby/manager.go` (`DisconnectGrace`, `DisconnectPlayer`,
`ResumePlayer`, `releaseHeldSeats`, `BeginShutdown`),
`internal/lobby/disconnect.go` (`pending` → `expiring`).

## 15. A second session displaces the first and closes it

*Generations 2026-09-06, `97eed0a`. Closing the displaced connection 2026-09-19, `f97b624`.*

**Context.** There used to be an `ErrAlreadyConnected`. A half-open TCP session -
a laptop that slammed shut - kept the account locked out of its own seat for the
whole 90-second grace window.

**Decision.** `SessionTracker.Connect(userID, conn)` bumps a per-account
generation and **closes the displaced connection**. Only the owning generation may
free the tracker slot or give up the lobby seat (`Owns` / `Release`).

**Consequences.** Reconnecting always works, which is the behaviour a player
expects. The close happens **outside** the tracker lock: a wedged peer must not
hold every other account's `Connect` behind it. A displaced session's teardown
must touch neither the seat nor the slot, or the new session loses both -
`releaseSession` returns early on `!Owns`. Capacity is still refused, with a
distinct `ErrServerFull`.

**Where.** `internal/ssh/server.go` `SessionTracker`, `releaseSession`.
`internal/ssh/lifecycle_test.go`
`TestSessionTracker_ConnectClosesTheDisplacedSession` and
`TestReleaseSession_GivesUpTheSeatBeforeTheSlot`.

## 16. Identity is an SSH key fingerprint

**Context.** The product promise is "no download, no browser, no account form".
That rules out a password, an email address and a reset flow.

**Decision.** Any public key is accepted. The identity is
`cryptossh.FingerprintSHA256(key)`, a `SHA256:…` digest. The raw public key is
never stored. The SSH login name becomes the username on first connect
(`ssh -l yourname tty.cards`).

**Consequences, stated plainly because they are permanent:**

- **A new key is a new account, so it is a rating reset.** There is no way to
  merge two accounts and no way to move a rating between keys.
- **Lose the key, lose the account.** No password reset, no second factor, no
  recovery.
- **The fingerprint is a cross-service correlator.** It is a hash, not the key -
  but the same key is usually the one on GitHub, so it is stable and linkable. It
  is authentication data, not a pseudonym, and the privacy notice says so.
- Because minting an identity is free, every anti-farm rule in this file exists.

**Where.** `internal/ssh/auth.go`, `internal/db/users.go`,
[`privacy.md`](privacy.md) §2, [`SECURITY.md`](SECURITY.md) "Out of scope".

## 17. Registration has its own limiter, and its own refusal

*2026-09-19, `f97b624`.*

**Context.** The auth limiter counts **auth attempts** (5 per second per network
by default) because an ssh-agent offers every key it holds. That is the wrong unit
for "how many accounts may this network create".

**Decision A - a second limiter.** `registrationLimit` = 5 per
`registrationWindow` = 1 hour, per client network. `LoadOrRegisterUser` takes an
`allowRegister func() bool` and consults it **only** on the `user == nil` branch,
so a returning player never spends the budget. Auth deliberately knows nothing
about how the budget is counted; it only asks.

**Decision B - the refusal says nothing.** `mapRegisterError` folds
`db.ErrUsernameTaken` and `db.ErrInvalidUsername` into one `ErrNameUnavailable`.

**Consequences.** Registration stays open - that is the point of a public demo -
but at a rate, not a floodgate. The uninformative refusal is the deliberate part:
a distinguishable message turns the login banner into a "does this account exist"
oracle over every username, to an entirely unauthenticated caller. The distinct
sentinels survive server-side, and `LoadOrRegisterUser` logs the real cause.
`ErrKeyAlreadyRegistered` **is** returned verbatim, because the key is the
caller's own and tells them nothing they could not learn by connecting again.

**Where.** `internal/ssh/auth.go` (the comments on `ErrNameUnavailable` and
`LoadOrRegisterUser`), `internal/ssh/server.go` `registrationLimit` /
`allowRegistration`.

## 18. TLS is not terminated here yet, and the apex cannot sit behind Cloudflare

*nginx config 2026-08-06, `35bb880`; still open.*

**Context.** The game is `ssh tty.cards` - the apex. The website is on
`www.tty.cards`, served by GitHub Pages behind Cloudflare.

**Decision.** The apex is **grey-clouded**: DNS only, not proxied. A
Cloudflare-proxied hostname resolves to Cloudflare's own IPs, and `ssh tty.cards`
would follow it there and fail. So the apex points at the VPS directly, nginx
terminates `:22` and `:80` on it, and everything that is not `/api/` is a 301 to
`www`.

TLS on the apex is **not yet configured**, and the `443` server block is present
but commented out.

**Consequences.** This is an open item, not a settled one, and it is recorded here
so nobody rediscovers the constraint. Because the apex is grey-clouded it needs a
*publicly trusted* certificate - a Cloudflare Origin CA certificate is only
trusted by Cloudflare, so it does not work here; certbot does. Until then the
website's live-stats panel, served over `https`, cannot call the plaintext
`http://tty.cards/api` origin and shows "server unreachable", which is at least
honest.

**Where.** `internal/config/nginx.conf` - the comment above the `:80` server block
and the commented `:443` block below it.

## 19. The backend speaks PROXY protocol, and `:6969` is never published

*2026-08-28, `ba30078`.*

**Context.** nginx terminates `:22` in a `stream {}` block and forwards to
`backend:6969`. Without PROXY protocol every connection would arrive from nginx's
container IP, and every per-network limit would be a single shared bucket.

**Decision.** `proxy_protocol on` in nginx; the backend wraps its listener in
`proxyproto.Listener`. The backend's `6969` and the stats API's `6970` are
`expose`-only on the compose network.

**Consequences.** **Publishing `:6969` is a real hole, not a nitpick.** A client
that can reach it directly forges the PROXY header and therefore its own source
address, and walks past every per-network limit. The same argument covers `:6970`
with `API_TRUST_PROXY=true`: nginx sets `X-Forwarded-For` from `$remote_addr`, not
`$proxy_add_x_forwarded_for`, so a client cannot prepend its own value - but only
while the client cannot reach the port. `API_TRUST_PROXY` therefore defaults to
**false** and compose opts in explicitly: the unsafe direction has to be chosen.

A bare local `ssh` client sends no PROXY header, so local development needs
`PROXY_PROTOCOL=false`.

**Where.** `compose.yaml` (the comment above `proxy.ports`),
`internal/config/nginx.conf`, `cmd/server/main.go` `serve`,
`internal/config/config.go`.

## 20. Every network limit keys on the IPv6 /64

*2026-08-07, `85f8099`.*

**Context.** A residential IPv6 customer is routinely handed a /64 - 2^64
addresses. A limiter keyed on the full address is a limiter keyed on nothing.

**Decision.** `ratelimit.NetKey` collapses an IPv6 address to its /64 and unmaps
v4-in-v6. nginx does the same with a `$client_net` map, which is duplicated across
the `stream` and `http` contexts because the two cannot share one.

**Consequences.** One household shares one bucket, which is also true of IPv4 and
is the behaviour the limits are sized for. `NetKey` itself is **total** - an
address it cannot parse comes back verbatim - and the fail-closed decision sits
one level up in `ssh.netKeyFor`, which returns `ok=false` for a nil address or a
`SplitHostPort` error. `rateLimitAuth` and `allowRegistration` both refuse on
`!ok` rather than sharing one bucket for every unkeyable peer.

**Where.** `internal/ratelimit/netkey.go`, `internal/ssh/server.go` `netKeyFor`,
`internal/config/nginx.conf` (both `$client_net` maps).

## 21. Grafana is loopback-only with no login

*2026-09-19, `bdeb20c` "loopback-only with no login; CI asserts the binding instead of a password".*

**Context.** An observability stack needs a UI. A Grafana with a password is a
password to rotate, store and leak; a Grafana on a public port is a public port.

**Decision.** Grafana publishes to `127.0.0.1:3000` only, with anonymous access as
Admin and the login form off. It is reached with
`ssh -L 3000:127.0.0.1:3000 <host>`.

**Why this is the safest choice here.** Reaching the port at all requires an SSH
session on the host, and anyone with that already owns the whole stack - the
database, the volumes, the process. A Grafana password would add a second
credential that protects nothing the host's SSH does not already protect, while
adding a thing to leak. The gate is the host, so make the host the gate and say
so.

**Consequences.** The binding is the entire security property, so **widening it
without adding authentication is a vulnerability**, and CI asserts it stays:
`.github/workflows/test.yml` has a step that fails if Grafana publishes anything
but `127.0.0.1:3000`. The comment in the workflow says why the assertion exists.

**Where.** `compose.yaml` (the `grafana` service), `.github/workflows/test.yml`
(the `compose` job), [`SECURITY.md`](SECURITY.md) "Hardening the deployment you
run".

## 22. Erasure anonymises the `users` row rather than deleting it

*2026-09-19, `56c561c`.*

**Context.** A player asks to be erased. Their `users` row is the parent of
`match_participants` rows that belong to *other* players' match history.

**Decision.** One transaction:

| Row | Action | Reason |
|---|---|---|
| `public_keys` | hard delete (`Unscoped`) | the unique `fingerprint` on a soft-deleted row would lock the person out of ever registering again; with the keys gone nothing can authenticate as the account |
| `rankings` | hard delete (`Unscoped`) | a soft-deleted ranking still holds the `(user_id, game_id)` primary key |
| `users` | **kept, anonymised**: `username` → `deleted_` + 32 hex of the UUID, `last_seen_at` → NULL | other players' history has to keep resolving to a name |
| `match_participants` | untouched | those rows are the other players' history, not this one's |

**Consequences.** Erasure is irreversible and does **not** remove the person from
other players' history - only their name from it. The privacy notice says so. The
`deleted_` form has to satisfy the column: `username` is `VARCHAR(40)` with a
CHECK allowing either ≤16 characters or exactly `^deleted_[0-9a-f]{32}$`, and
`ValidateUsername` refuses the prefix so nobody can squat it. The `users` row is
updated **by column**, not `Save`d from a loaded struct, because the save hooks
would walk the associations the transaction just deleted and write them back. The
leaderboard cache is cleared wholesale afterwards: a five-minute TTL is five more
minutes of an erased name on screen.

**Where.** `internal/repository/user.go` `DeleteAccount` / `eraseUserLocked`,
`internal/db/users.go` `AnonymisedUsername` / `ValidateUsername`,
`internal/db/migrations/000001_init.up.sql` (`username_valid`),
`internal/tui/views/profile/profile.go` (the `x` → type `DELETE` flow).

## 23. Retention is a number in a file, not "until the disk fills"

*2026-09-19, `46c5e68`.*

**Context.** The observability stack held application logs with client network
prefixes and player ids, and traces that used to join an IP to an account. Nothing
expired.

**Decision.** Explicit, per signal:

| Signal | Kept | Set in |
|---|---|---|
| Logs (Loki) | **14 days** | `internal/config/loki/loki.yaml` `retention_period: 336h` + compactor retention |
| Traces (Tempo) | **48 hours** | `internal/config/tempo/tempo.yaml` `block_retention: 48h` |
| Metrics (Prometheus) | **30 days**, 8 GB cap | `compose.yaml` `--storage.tsdb.retention.time=30d` |
| Container stdout | 3 × 10 MB | `compose.yaml` `x-logging` (a size bound, not a time bound) |

**Consequences.** Traces get the shortest window on purpose: the `ssh.session`
span is the strongest identifier in the system. Two further decisions hang off the
same reasoning and belong with it - the session span carries **no client address**
(the comment in `startSession` says joining an IP to an account for 48 hours is
the record a trace store should not hold), and connect/disconnect logs carry
`client_net`, the /64, with the full `remote_addr` surviving only on WARN and
ERROR where abuse investigation needs it. nginx contributes nothing: the `stream`
block is `access_log off` and the `http` block uses a `log_format privacy` with no
`$remote_addr` and no User-Agent.

Metrics carry no personal data at all, and that is **enforced**:
`internal/observability/metrics_test.go` collects every instrument and fails if
any attribute key falls outside a fixed allow-list.

**Where.** The table above, plus [`data-inventory.md`](data-inventory.md) for the
per-field version.

## 24. `Pile.Shuffle()` returns nothing

**Context.** `Shuffle` used to return an `error`, and every caller plumbed it
through - `OnGameStart`, the reshuffle helpers, the poker deal.

**Decision.** It returns nothing. It seeds a `math/rand/v2` ChaCha8 generator once
per call from `crypto/rand`, which **since Go 1.24 cannot fail**: `crypto/rand.Read`
aborts the process on an OS failure rather than returning an error.

**Consequences.** The error every caller handled was an unreachable branch dressed
as resilience - a guard that looked like defence and was in fact noise. Several
such guards were removed across the engine and the rules packages in the same
pass, each site left with a comment saying why it could not fire. That is the
general rule this repo follows: **if a guard is unreachable, delete it and say so,
rather than documenting it as defence.**

**Where.** `internal/deck/deck.go` `Shuffle` and its comment.
[`CONTRIBUTING.md`](CONTRIBUTING.md) "Code style" states the general rule.

## 26. The layer rules are enforced by `depguard`

## 27. CI runs `-shuffle=on` and a deadcode gate

*2026-09-19, `bdeb20c`.*

**Context.** Go runs tests in source order by default, which lets an
order-dependency hide. And unused exported code accumulates quietly in a repo
with this many small packages.

**Decision.** The `test` and `integration` jobs run `go test ./... -race
-shuffle=on -count=1`. A separate step runs
`golang.org/x/tools/cmd/deadcode@v0.50.0 -test ./...` and fails on output.

**Consequences.** `-shuffle=on` means a test that depends on another test having
run first fails eventually rather than never, and `-count=1` keeps the cache from
hiding it. The deadcode gate is what keeps the "delete the unreachable guard" rule
from being aspirational; it is pinned to a version so a tool release cannot turn a
green pipeline red on a commit that touched nothing.

**Where.** `.github/workflows/test.yml`.

## 28. Size gates: split the function, do not raise the threshold

*2026-08-01, `f1b2bad` "enable size gates and lint test files".*

**Context.** `funlen`, `cyclop`, `gocognit`, `nestif` and `lll` all have a number,
and any number can be argued up one commit at a time until it means nothing.

**Decision.** Each threshold sits **just above the worst surviving function**:
`funlen` 75 lines / 55 statements, `cyclop` 21, `gocognit` 30, `nestif` 9, `lll`
140. A new violation therefore means your function is now the worst one in the
repo. Split it. Raising a threshold to land a change is not accepted in review.

**Consequences.** The numbers are meaningful precisely because they are tight, and
they only stay meaningful if nobody moves them. `cyclop: 21` even carries a
comment naming the function it is calibrated against. Tests are excluded from all
five: a table-driven test is legitimately long and repetitive, and its branchiness
is not a maintenance signal.

**Where.** `.golangci.yml` `settings`, [`CONTRIBUTING.md`](CONTRIBUTING.md) "Size
gates".

## 29. There is no outbox table for match finalization

*2026-09-19, `65b6f52`.*

**Context.** A ranked match is written asynchronously by a finalizer goroutine. A
deploy in the wrong second loses it.

**Decision.** Two bounded drain windows on shutdown (15 s, then another 15 s with
a warning), not a durable outbox.

**Consequences.** The rejected alternative - an outbox table written at game end
and drained on boot - buys nothing here that the grace window does not: the write
it protects is one short transaction against a database in the same compose
project. What it costs is a schema, a drain path, and a second way for a match to
be recorded. Two things make the trade honest and both are checked: compose's
`stop_grace_period` (80 s) must exceed the whole sequential drain (30 s SSH + 5 s
API + 2×15 s here + 5 s OTel = 70 s), or the runtime SIGKILLs the process
mid-write; and the give-up is **not silent** - it logs at ERROR and counts
`MatchFinalize(outcome="dropped")`, which is alertable. The residual risk is
stated rather than removed: a match that finishes in the last seconds of a deploy,
whose write then blocks for 30 seconds, is lost from history.

**Where.** `cmd/server/main.go` `waitForFinalizers` - the comment is the record.

## 30. GORM tags that look like schema enforcement were removed

*2026-09-19, `56c561c`.*

**Context.** The models carried `uniqueIndex`, `not null`, `default`, `check` and
`type` tags. Nothing calls `AutoMigrate` - `internal/db/migrations` owns the
schema - so those tags enforced nothing, and one of them had already drifted from
the SQL.

**Decision.** Delete them. Only the tags GORM actually uses to build queries
remain: `primaryKey`, `foreignKey`, `autoIncrement`, `serializer`.

**Consequences.** Nothing in the struct now reads like a guarantee it does not
make. The guarantee is re-established from the other direction:
`TestSchemaNullabilityMatchesStructs` derives what the SQL must enforce **from the

**Where.** `internal/db/users.go` (the comment above `User`),
`internal/db/gorm_test.go`.

## 31. The odd chip in a split pot goes to the lowest-sorted player ID

*2026-08-28, `3d5a40d`.*

**Context.** A pot that does not divide evenly among its winners leaves one or
more odd chips.

**Decision.** `splitEvenly` hands the odd chips one each to the front of the id
slice, and callers sort the ids first.

**Consequences.** This is a **deviation from casino practice**, named as such in
the code: a casino gives the odd chip to the first player left of the button.
This gives it to the lowest-sorted player ID. It is deterministic, which is what
matters for a table that has to be replayable in a test, and the amount at stake
is one chip out of a 1000-chip stack.

**Where.** `internal/game/poker/streets.go` `splitEvenly`.

## 35. Migration 000004 backfills some columns and refuses to backfill others

**Context.** Four columns whose Go field is a plain scalar could still be NULL, so

## 36. nginx has two health endpoints and duplicates one map

**Context.** Both the backend container and the proxy container need a
healthcheck, and the proxy passes `/api/` through wholesale.

**Decision A.** `/api/healthz` is returned 404 by nginx. It pings the database on
every request and exists only for the *backend* container's own healthcheck, which
reaches it on loopback inside the compose network. Exposed through the proxy, any
caller could spend a database round-trip per request.

**Decision B.** `/healthz` on the proxy is a static string with no upstream and

the healthcheck runs against `127.0.0.1` with no `Host` of its own.

**Decision C.** The `$client_net` map is written twice, once in `stream {}` and
once in `http {}`. nginx cannot share a map across the two contexts, so this is a
deliberate duplicate rather than an oversight - if you change one, change both.

## 37. A rules panic on the turn timer ends one table, not the process

*2026-09-20, `7cf2423` "a rules panic on the turn timer ends one table, not the process".*

**Context.** `onTurnTimeout` runs on a goroutine `time.AfterFunc` started, and
nothing above it recovers. A panic in any rules hook reached from there -
`TimeoutAction`, `ValidateAction`, `ApplyAction`, `AfterAction`, a leave handler -
would take the whole process down: every table in memory, for one game package's
defect.

**Decision.** `Engine.recoverRulesPanic` is a direct `defer` on that goroutine. It
logs the panic with `debug.Stack()`, re-takes `e.mu`, and if the game is still
`Playing` on a live engine calls `finishGameLocked(nil, EndReasonRulesError)`.

**Consequences.** An auto-play panic now gets exactly the treatment a rules error
from `SubmitAction` gets: the table ends, the match is recorded **unrated**
(§[11](#11-three-end-states-are-recorded-without-elo)), and every other table
keeps playing. Re-taking the lock in the recover is safe because the locked
helpers release `e.mu` in their own defers as the panic unwinds. This is a
backstop, not a licence: rules are still expected not to panic, and the
`TestSoak_TimeoutActionIsAlwaysLegal` soaks and `FuzzBestMeldSplit` exist to keep
them from doing so. `bestSplitBy`'s over-long-hand guard in
`internal/game/ginrummy/melds.go` still returns the whole hand as deadwood rather
than panicking; its comment predates this recover and now understates the
blast-radius reduction, but the guard itself is still the right behaviour.

**Where.** `internal/game/turnclock.go` `onTurnTimeout` / `recoverRulesPanic`.
Test: `internal/game/engine_timeout_test.go`
`TestEngine_TurnTimeout_RulesPanicEndsOnlyThisTable`.
